I used OpenAI Codex to investigate this locally on main at `e2fcc412` and the released `fastmcp[apps]==4.1.0` wheel, with Python 3.14.7 and prefab-ui 0.20.2. Codex ran an in-memory `Client(server)` probe with six `PrefabAppConfig` tools. With `PREFAB_BUNDLED_RENDERER=1`, all six distinct resource URIs returned byte-identical HTML: 6,646,438 UTF-8 bytes per read, or 39,878,628 bytes across six reads. Without that setting, the default renderer was a 471-byte version-pinned CDN stub. Listings contained no HTML. These are resource-response payload sizes; I don't have browser/network measurements or evidence of host cache savings, and the probe did not reproduce the reporter's patched renderer or Claude Desktop setup.

Codex also ran the existing app-related tests on unchanged main: 159 passed and 2 xfailed. The 13 renderer-synthesis tests passed separately in bundled mode. No framework source changes were made.

Given the intentional per-tool CSP design in #3824 and the resource-level domain/border fix in #5611, I propose sharing only automatically synthesized Prefab resources whose renderer content, MIME type, and complete effective resource metadata match. Different CSP, permissions, domains, border preferences, or other meaningful metadata would remain distinct; explicit resource URI overrides would stay untouched. Existing per-tool URIs should remain readable as aliases, and backend tool identity hashes should stay independent. Regression coverage would check equal-config sharing, differing-config isolation, explicit overrides, legacy reads, and mounted tools. A shared URI would only enable reuse by compatible hosts; it would not prevent explicit repeated reads.

Would maintainers support that resource identity/design approach before implementation? I understand the issue reporter has first claim on implementing an accepted design.
